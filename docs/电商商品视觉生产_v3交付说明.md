> **产品定位**：面向中小电商卖家 / 运营的「自然语言电商修图工作台」

> **文档版本**：v3.0（2026-10-16）  
> **对应里程碑**：M2 工具 + SSE  
> **一句话目标**：**在编辑器里手动修图（去背/调色等）→ Worker 异步执行 → SSE 看进度 → 画布更新 → 可导出**  
> **关联文档**：  
> - `电商商品视觉生产_版本规划与v1交付说明.md`  
> - `电商商品视觉生产_v2交付说明.md`、`v2_第二版完成总结.md`

> - 参考仓库：[yuyuanweb/ai-picture-editor](https://github.com/yuyuanweb/ai-picture-editor)（对照 ToolRegistry / ARQ / SSE，**裁剪范围，不整仓复制**）  
> **协作方式**：从 `version2` 拉出 `version3`（或 `feat/v3-tools`），完成后打 tag `v3.0.0` 并推送 GitHub

## 1. v3 在整条版本线里的位置

```text
v1 骨架 → v2 看见商品图 → ★ v3 能手动修 → v4 能说话修
                                              ↓
v8 部署验收 ← v7 图层 ← v6 选区 ← v5 文生图 ←─┘
```

| 版本 | 里程碑 | 用户能感知到什么 |
|------|--------|------------------|
| v1 | M0 | 系统能启动，health 通 |
| v2 | M1 | 上传后画布看得见商品图 |
| **v3（本文）** | **M2** | **点工具栏能修图，有进度，结果回到画布，能导出** |
| v4 | M3 | 自然语言 → 计划卡片 → 确认执行 |

v3 把编辑器从「相册预览」变成「能干活的修图台」。没有手动工具 + 异步执行闭环，v4 Agent 就没有可调用的工具真相源。

## 2. 为什么第三版做「工具 + Worker + SSE + 导出」？

### 2.1 原则（延续 v1/v2）

1. **每版可演示**：验收题是「点去背/调色，看到进度，画布变了，能导出」，不是半截 Registry。  
2. **耗时任务不堵 API**：规划书 8.1——抠图/滤镜进 **ARQ Worker**，请求只返回 `run_id`。  
3. **ToolRegistry 唯一真相源**：规划书 8.2——UI 与（未来）Agent 共用同一套工具定义；路由禁止第二套修图逻辑。  
4. **进度靠 SSE**：Worker 经 Redis Pub/Sub 发事件，前端订阅后刷新进度条与画布。  
5. **仍不写 Agent**：LangGraph / 计划卡片留给 v4；本版只做「人手点工具」。

### 2.2 v3 明确不做（留给后续版本）

| 不做 | 放到哪一版 | 原因 |
|------|------------|------|
| LangGraph、计划卡片、确认执行 | v4 | 依赖本版 Registry + 入队能力 |
| 文生图创作页 | v5 | 另一入口 |
| 矩形/笔刷选区、局部编辑 | v6 | 画布交互加重 |
| 主体/背景拆层、完整图层面板 | v7 | 图层模型可后续扩展 |
| 强制登录、COS 真接通、Docker 应用 | v8 / 增强 | 不阻塞「能手动修」 |
| 参考仓库全量 20+ 工具 | 增强 | 一期 4～6 个够演示 |

## 3. 第 3 版要完成什么？（验收标准）

完成 v3 后，你应能：

1. 在已有会话的编辑器中看到**工具栏**（至少：调色、去背、翻转或旋转、导出）。  
2. 点击工具后，后端 `POST /api/sessions/{id}/tools/{tool_name}` **立即返回 `run_id`**（不长时间卡住 HTTP）。  
3. 另开进程跑 **ARQ Worker**；Worker 执行像素处理，写新资产并更新 `session.document`。  
4. 前端通过 **SSE**（建议 `GET /api/events/{run_id}` 或规划约定路径）收到 `progress` / `completed` / `error`。  
5. 完成后画布刷新为新结果图。  
6. **导出**：能下载当前主图层结果（新文件或触发浏览器下载）。  
7. 库中有 `tool_runs` 表（Alembic 新迁移），可查状态 `queued|running|succeeded|failed`。  
8. README 写明：需同时启动 API + Worker；提交 GitHub，tag 建议 `v3.0.0`。

**验收一句话**：上传图进编辑器 → 点「调色/去背」→ 进度条走动 → 画布更新 → 点导出拿到文件。

## 4. 主流程（用户路径）

```text
用户在 Editor 点「去背景」
  → POST /api/sessions/{id}/tools/remove_background  {params}
  → services/tools：校验工具名 → 写 tool_runs(queued) → ARQ enqueue
  → 立即返回 { run_id }

前端：
  → 订阅 GET /api/events/{run_id}（SSE）
  → 显示进度条

Worker（独立进程）：
  → 取 job → tool_runs=running
  → 读当前图层图 → 执行工具（Pillow / mock 去背）
  → 新图写入 storage + 新 assets 行
  → 更新 session.document 主图层 asset_id / asset_key
  → Redis publish progress / completed

前端收到 completed：
  → 重新 GET session 或按事件里的 asset 刷新 CanvasStage
```

## 6. 后端：v3 要完成哪些文件？

### 6.1 分层为何这样切

| 层 | 职责 | 为什么 |
|----|------|--------|
| `tools/` | 工具元数据 + executor | UI/未来 Agent 唯一入口 |
| `edits/` | 纯 Pillow 算法 | 可单测、无 HTTP/DB 耦合 |
| `services/tools.py` | 校验 → 写 tool_runs → enqueue | 事务与用例边界 |
| `queue.py` + `worker.py` + `tasks/` | 异步执行 | API 不被抠图拖死 |
| `events.py` + `routers/events.py` | Pub/Sub + SSE | 进度实时回前端 |
| `models/tool_run.py` | 执行记录 | 可查询、可幂等（job_id=run_id） |

### 6.2 一期工具清单（必须 / 建议）

对齐规划书 8.2，**v3 最少做下面 4 个**；有余力再加旋转/裁剪。

| name | 中文 | 实现建议 | 是否入队 |
|------|------|----------|----------|
| `adjust_image` | 调色（亮度/对比度/饱和度即可） | Pillow，`edits/pixels.py` | 是 |
| `remove_background` | 去背景 | **优先 mock**（简单抠四角/白底近似）或可选 rembg | 是 |
| `flip_layer` | 水平翻转 | Pillow | 是（或够快可同步，建议仍入队统一） |
| `export_image` | 导出当前主图层 | 读 storage → 返回下载 URL / 文件流 | 可同步（低耗时） |

> **去背策略建议**：v3 默认 `MATTING_PROVIDER=mock`，保证无重型模型也能演示；文档注明可选安装 rembg。不要在 v3 把「装 onnx 跑不通」变成阻塞项。

### 6.3 必须完成的后端文件清单

| 文件 | 职责 | v3 要做到什么 |
|------|------|----------------|
| `models/tool_run.py` | ORM | id, session_id, tool_name, params, status, progress, result_ref, error, 时间戳 |
| Alembic 迁移 | DDL | 建 `tool_runs` + 索引 |
| `tools/base.py` | ToolSpec | name/label/description/params_schema/executor/ui_exposed |
| `tools/registry.py` | 注册表 | `get` / `list_ui_tools` / 未知工具报错 |
| `tools/retouch.py` 等 | 具体工具 | 调 `edits`，写新 asset，更新 document |
| `edits/pixels.py` | 算法 | adjust / flip / mock_matting |
| `queue.py` | ARQ | `enqueue("run_tool", run_id)`，job_id=run_id 防重复 |
| `worker.py` | Worker | `WorkerSettings`，functions 含 `run_tool_task` |
| `tasks/tools.py` | 任务 | 按 run_id 加载 → 调 registry executor → 发事件 |
| `events.py` | Pub/Sub | `publish(run_id, payload)` / `subscribe` |
| `services/tools.py` | 入队用例 | 校验 session+工具+参数 → insert tool_run → enqueue |
| `routers`（sessions 或 tools） | HTTP | `POST .../tools/{name}` → `{run_id}`；`GET /api/tools` 列表可选 |
| `routers/events.py` | SSE | 按 run_id 推送 progress/completed/error |
| `schemas/run.py` | 契约 | 入队响应、事件 payload |
| `pyproject.toml` | 依赖 | **必须** `arq`；rembg 可选 |

### 6.4 接口契约（v3 冻结范围）

在 v2 接口之上新增：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/tools` | （可选）返回 UI 可展示工具元数据 |
| POST | `/api/sessions/{id}/tools/{tool_name}` | body=params → `{run_id}` |
| GET | `/api/events/{run_id}` | **SSE** 进度流 |
| GET | `/api/runs/{run_id}` | （可选）轮询兜底查状态 |
| GET | `/api/sessions/{id}/export` | （或 tools/export）下载当前结果 |

**SSE 事件约定**（对齐规划书 10.1，可精简字段）：

```text
event: progress
data: {"run_id":"...","progress":40,"message":"处理中"}

event: completed
data: {"run_id":"...","session_id":"...","asset_id":"..."}

event: error
data: {"run_id":"...","message":"..."}
```

### 6.5 `tool_runs` 表（最小字段）

对齐规划书 7.2，v3 落地：

| 字段 | 说明 |
|------|------|
| `id` | UUID，同时作 ARQ job_id |
| `session_id` | FK → edit_sessions |
| `tool_name` | 注册表内名称 |
| `params` | JSONB |
| `status` | queued / running / succeeded / failed |
| `progress` | 0～100 |
| `result_ref` | 结果 asset storage_key 或 asset_id |
| `error` | 失败信息 |
| `created_at` / `finished_at` | 时间 |

### 6.6 与参考仓库的对齐与差异

| 点 | 参考仓库 | image100 v3 |
|----|----------|-------------|
| ToolSpec / Registry | 完整、工具很多 | **对齐结构**，只注册 4～6 个 |
| ARQ + Redis | 有 | **对齐**（Redis 已有 7312） |
| SSE | `/events` 等 | **对齐思路**；路径按本文 `/api/events/{run_id}` |
| 去背 | rembg 等 | **默认 mock**，rembg 可选 |
| Agent / 计划 | 已有 | **不做**（v4） |
| 存储 | MinIO | 继续 **local** `data/` |

## 8. 进程与启动方式（v3 关键变化）

开发期需要 **两个后端进程**：

```bash
# 终端 1：API
cd backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 7302

# 终端 2：Worker
cd backend
python -m arq app.worker.WorkerSettings
# 或：arq app.worker.WorkerSettings

# 终端 3：前端
cd frontend
npm run dev
```

README 必须写清：只开 API 不开 Worker 时，工具会一直 queued。

## 9. v3 推荐开发顺序

1. 依赖：`arq` 写入 `pyproject.toml` 并安装。  
2. `models/tool_run.py` + Alembic 迁移并 `upgrade head`。

4. `tools/base.py` + `registry.py` + `retouch.py` / `canvas.py`。  
5. `queue.py` + `worker.py` + `tasks/tools.py`（先 curl 入队，Worker 日志能跑通）。  
6. `events.py` + `routers/events.py`（SSE 用 curl 或简单 HTML 测）。  
7. `services/tools.py` + `POST .../tools/{name}`。  
8. 前端工具栏 + SSE hook + 画布刷新。  
9. 导出接口与按钮。  
10. README、联调、提交 `version3` / tag `v3.0.0`。
