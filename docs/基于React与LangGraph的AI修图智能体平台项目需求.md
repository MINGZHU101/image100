# 一、这个项目是做什么的

**通俗一句话定义**：

这是一个 **AI 智能修图服务系统**，不是让用户在一堆按钮里自己找功能，而是通过 **LangGraph 智能体** 理解自然语言修图指令，自动规划步骤、调用统一工具库完成抠图、调色、变换、局部编辑等操作，再配合 **React + Konva 专业画布** 实时展示结果，打造一个可本地/Docker 部署的 AI 修图工作台。

**区别于普通在线修图网站 / 普通 ChatGPT 问答的核心亮点**

1. **普通修图网站**：用户必须自己找菜单、调参数，**不会理解「把背景换成海滩」这类自然语言**；

2. **普通大模型聊天**：会「口头教你怎么修」，但 **不会真正改像素、不会调用抠图/扩图工具、不会管图层与选区**；

3. **本项目（修图智能体）**：具备 **规划—校验—确认—执行** 能力，能 **拆解复杂指令、选择工具、补齐参数、异步执行并回传画布**，UI 按钮与 Agent **共用同一套工具注册表**，工程结构清晰、可扩展、可演示。

# 二、项目背景与痛点

## 2.1 行业与学习场景痛点

- **专业修图门槛高**：Photoshop 等工具学习成本大，电商主图、证件照、简单去背等高频需求却很刚需；

- **AI 生图与修图割裂**：很多产品只会文生图，或只会滤镜；「生成 → 精修 → 导出」闭环不完整；

- **Agent 项目容易做成玩具**：只会聊天不会调工具，或工具与 UI 各写一套，难写进简历、难部署；

- **全栈 + 异步 + 画布交互复杂**：耗时任务卡死接口、进度无反馈、画布状态丢失，是真实工程痛点；

- **部署环境受限**：课程/个人项目最终要落在 Linux Docker（本项目目标为 CentOS 虚拟机），需要从需求阶段就考虑容器化。

## 2.2 项目解决的核心问题

用 **React 画布工作台 + FastAPI 异步服务 + LangGraph 修图智能体 + 统一 ToolRegistry** 解决：

**「会聊天不会修图、会修图不会智能规划、前后端与部署割裂」** 的问题，交付一套可分期实现、可 Docker 部署的 AI 修图智能体平台。

## 2.3 项目边界（做什么 / 不做什么）

| 属于本项目 | 不属于本项目（或远期） |
|------------|------------------------|
| 单用户/小团队修图工作台 | 大型 SaaS 多租户计费 |
| 自然语言驱动的工具调用 | 视频剪辑、3D 建模 |
| 静态图片编辑与导出 | 实时摄像头流处理 |
| 可选接入云端生图/编辑 API | 自研底层扩散模型训练 |
| Docker 一键部署到 CentOS | K8s 大规模集群运维 |

# 三、系统整体架构

整体五层架构：**资源存储层 → 业务服务层 → 智能体编排层 → 实时通道层 → 前端展示层**

```text
┌─────────────────────────────────────────────────────────────┐
│  前端展示层（React 19 + react-konva + Zustand）              │
│  落地页 / 创作页 / 编辑器 / 对话计划卡片 / 工具栏 / 画布     │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST + SSE
┌───────────────────────────▼─────────────────────────────────┐
│  实时通道层（Redis Pub/Sub + SSE）                           │
│  任务进度、步骤完成、错误、画布刷新通知                      │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  智能体编排层（LangGraph + LangChain）                       │
│  意图理解 → 多步计划 → 服务端校验 →（人确认）→ 调度执行     │
└───────────────────────────┬─────────────────────────────────┘
                            │ ToolRegistry
┌───────────────────────────▼─────────────────────────────────┐
│  业务服务层（FastAPI + Services + ARQ Worker）               │
│  会话 / 资产 / 工具执行 / 导出 / Provider（mock/云端）       │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  资源存储层                                                  │
│  PostgreSQL（业务） · Redis（队列/消息） · MinIO/本地（图片）│
└─────────────────────────────────────────────────────────────┘
```

## 1、资源存储层

| 存储 | 存放内容 | 说明 |
|------|----------|------|
| PostgreSQL | 用户、资产元数据、编辑会话、图层文档(JSONB)、工具运行记录、Agent 运行记录 | 会话级状态可恢复 |
| Redis | ARQ 任务队列、Pub/Sub 事件、短期缓存 | 支撑异步与 SSE |
| MinIO 或本地磁盘 | 原图、中间结果、遮罩、导出文件 | 通过 Storage 抽象访问 |

处理动作：上传校验 → 持久化对象 → 写元数据 →（可选）生成缩略图。

## 2、业务服务层（FastAPI）

整个系统的「业务中台」，负责：

- 资产上传与访问 URL 签发  
- 编辑会话生命周期（创建、读取、更新文档）  
- 工具调用编排（同步校验 + 异步执行）  
- 与 Provider 交互（文生图、图像编辑、对话规划）  
- 鉴权（分期引入）与健康检查  

## 3、核心智能层：LangGraph 修图智能体

整个系统的「大脑」，负责智能推理与计划，而不是直接在图里无校验地乱调工具：

- 用户指令理解（结合画布上下文：尺寸、图层、是否有选区）  
- 工具选择与多步计划生成  
- 服务端校验（工具是否存在、参数是否合法、依赖是否成环）  
- 人机协作：计划卡片确认 / 取消 /（增强）单步重试  
- 执行阶段按依赖顺序调度 ToolRegistry  

**框架分工**：

- **LangGraph**：状态机编排（plan → verify → …）  
- **LangChain**：ChatModel、消息、工具 schema 绑定  
- **不采用**多角色「律师团式」多智能体；本项目是 **单修图 Agent + 多工具**，更贴合业务。

## 4、工具能力层（ToolRegistry）

真实修图能力拆为可插拔工具，**UI 与 Agent 共用**：

### 工具组 A：基础变换（一期优先）

裁剪、旋转、翻转、缩放/移动（按实现难度裁剪子集）。

### 工具组 B：色彩与增强（一期优先）

亮度 / 对比度 / 饱和度 / 色温等（可先做 3～5 个滑杆参数）。

### 工具组 C：抠图与背景（一期或二期）

一键去背景；换背景（依赖云端或模板合成，可 mock）。

### 工具组 D：区域编辑（二期）

选区（矩形/笔刷）内调整；局部消除 / 局部替换（增强）。

### 工具组 E：图层（二期及以后）

主体/背景拆分；图层显隐排序；文字层（可选）。

### 工具组 F：生成与批量（三期可选）

文生图、营销图、批量套用同一流水线。

## 5、前端展示层（React）

用户 Web 界面建议页面：

| 页面 | 作用 | 演示价值 |
|------|------|----------|
| **落地页** | 产品介绍 + 开始创作入口 | 对外展示 |
| **登录页**（可二期） | 注册/登录 | 多用户隔离 |
| **创作页** | 文生图提示词 / 上传本地图 | 进入工作台的两条路径 |
| **候选图页**（可与创作合并） | 四宫格挑选 | 文生图故事线 |
| **编辑器页** | 画布 + 工具栏 + Agent 对话 + 计划卡片 +（可选）图层面板 | **核心演示页** |
| **批量/营销页**（可选增强） | 扩展业务 | 简历加分项 |

### 编辑器页交互说明（需求级）

- **画布区**：显示当前作品；支持缩放、平移；工具执行后自动刷新。  
- **工具栏**：手动触发与 Agent 同源的工具（如去背、调色）。  
- **对话区**：输入自然语言；展示 Agent 回复与结构化计划步骤。  
- **计划卡片**：列出将调用的工具与简要参数；提供「确认执行 / 取消」。  
- **进度区**：SSE 驱动的进度条或步骤状态（排队中 / 执行中 / 成功 / 失败）。  
- **会话侧栏**（可简）：历史编辑会话列表。  

内置 3 个完整演示场景（便于答辩/验收）：

1. **电商去背**：「去掉背景，主体居中一点」→ 计划含去背 + 简单变换或调色。  
2. **光线微调**：「提高亮度和对比度」→ 单步或两步 adjust。  
3. **上传精修**：本地上传 → 手动抠图 → 再对 Agent 说「再鲜艳一点」。

# 四、核心业务流程

## 4.1 完整闭环（自然语言修图）

1. 用户进入编辑器（上传图或选中生成图）；  
2. 在对话框输入修图需求；  
3. 后端组装画布上下文，调用 LangGraph：`plan → verify`；  
4. 前端展示计划卡片；  
5. 用户确认后，服务端按依赖顺序投递工具任务；  
6. Worker 执行工具，更新会话文档与图片资源；  
7. 通过 SSE 推送进度与完成事件；  
8. 前端刷新画布；用户可继续对话或导出。

## 4.2 手动工具闭环

1. 用户在工具栏选择工具并提交参数；  
2. 后端校验 → 入队 → Worker 执行；  
3. SSE 进度 → 画布更新。  

（与 Agent 共用执行引擎，仅入口不同。）

## 4.3 文生图闭环（分期）

1. 用户输入提示词；  
2. 异步生成 N 张候选（mock 或云端）；  
3. 用户挑选一张创建编辑会话；  
4. 进入自然语言/手动精修。

## 4.4 部署闭环（验收必须）

1. 在 CentOS 虚拟机拉取代码与 `.env`；  
2. `docker compose` 启动依赖与应用；  
3. 浏览器访问虚拟机 IP 对应端口；  
4. 跑通「上传 → Agent 修图 → 看到结果」。

## 5.2 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 交互接口 P95 < 300ms（不含模型推理）；耗时任务必须异步 |
| 可用性 | Mock 模式下全流程可演示；真实 Key 可增强效果 |
| 可维护性 | 工具新增不改 Agent 主图结构，只注册工具 |
| 可部署性 | Docker Compose 在 CentOS 可拉起；环境变量注入密钥 |
| 安全 | 生产环境必须更换 JWT/密钥；上传类型与大小限制；工具参数校验防任意代码执行 |
| 可观测 | 结构化日志；任务 run_id 可追踪；health 检查依赖 |
| 兼容 | 后端 Python 3.13；前端现代浏览器（Chrome/Edge 最新两个大版本） |

## 5.3 智能体行为需求

1. **只能调用已注册工具**，不得编造工具名。  
2. **能一步完成的不拆成多步**；一期建议最多 5～8 步。  
3. **缺参时优先用画布上下文推断**，避免无意义反问。  
4. **计划必须经服务端校验**后方可进入确认态。  
5. **高风险/多步计划默认需用户确认**；低风险单步是否自动执行可作为配置项（默认关闭更安全）。  
6. **失败时返回可读中文错误**，不泄漏内部堆栈给前端普通用户。  
7. **限制模型调用次数**（防死循环烧钱），例如单次用户指令规划仅 1 次 LLM（一期）。

# 六、项目创新点

1. **技术创新：LangGraph 计划图 + 服务端强校验**  
   不是裸聊，也不是不可控自动乱点工具，而是「先规划、再校验、后执行」。

2. **架构创新：UI 与 Agent 共享 ToolRegistry**  
   一处定义工具元数据与执行器，避免双轨维护，工程示范性强。

3. **交互创新：人机协作计划卡片**  
   复杂修图步骤可视化确认，体现 Agent 产品设计而非纯模型调用。

4. **工程创新：异步队列 + SSE 实时反馈**  
   贴合真实 AI 应用耗时特征，适合写进项目汇报与面试。

5. **落地创新：React 精简重构 + CentOS Docker 部署**  
   在原 React 教程项目基础上按期砍减与优化，并明确 Linux 容器化验收环境。

6. **成本创新：Mock Provider 一等公民**  
   无 GPU、无 API Key 也能完成开发、演示与大部分测试。

# 九、接口需求（概要）

> 详细字段在实现时以 OpenAPI 为准；此处约束范围。

1. `GET /api/health` — 依赖探测  
2. `POST /api/assets` — 上传  
3. `GET /api/assets` — 列表  
4. `POST /api/sessions` — 创建编辑会话  
5. `GET /api/sessions/{id}` — 获取会话与文档

# 十三、常见疑问

## 1、这个项目难度大吗？

**难度适中、可繁可简**：  
- 保底：上传 + 画布 + 几个本地工具 + Mock Agent 计划；  
- 拔高：LangGraph 校验、SSE、图层、云端生图、CentOS 部署。  
保底能做完，上限足够做课程设计/简历项目。

## 2、和普通「AI 画图网页」有什么区别？

普通项目：多为单次生图或滤镜；  
本项目：**会规划、会调工具、会异步执行、会画布协同、可 Docker 部署**，技术链完整。

## 3、为什么用 LangGraph 而不是只上 LangChain？

修图指令需要 **多步计划、服务端校验、人确认再执行**。LangGraph 适合这种有状态工作流；LangChain 负责模型与工具描述。二者组合比堆更多 Agent 框架更合适。

## 4、为什么前端继续用 React？

原开源教程前端已是 **React 19 + react-konva**，画布与编辑器是最重的一块。本项目默认沿用原栈，把工期留给 Agent、异步链路与 CentOS Docker 部署，避免无必要的框架重写。

## 5、没有 GPU / 没有 API Key 能做吗？

能。默认 **Mock Provider**：本地 Pillow/色块图模拟结果，照样演示计划卡片与 SSE。有 Key 再切换云端增强。

## 6、数据与模型从哪来？

- 用户上传图片与（可选）云端 API 生成结果；  
- 本地算法：Pillow/rembg 等开源组件；  
- 不强制自建大规模训练数据。

## 7、要不要做成法律项目那种「五个智能体页面」？

**不需要。** 法律项目适合按业务角色拆多 Agent；修图项目更适合 **单 Agent + 多工具 + 单编辑器工作台**。页面以编辑器为中心，而不是五个独立 Agent 站点。
