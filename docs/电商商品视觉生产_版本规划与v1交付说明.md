# 电商商品视觉生产 — 版本规划与第 1 版（v1）交付说明

> **产品定位**：面向中小电商卖家 / 运营的「自然语言电商修图工作台」  
> **工程代号**：`image100`  
> **文档版本**：v1.0（2026-10-14）  
> **关联文档**：`AI修图智能体_项目规划书.md`、需求文档、重构方案  
> **协作方式**：按版本迭代开发，**每完成一版提交一次 GitHub**

---

## 1. 总体打算用几版做完？

结合规划书里程碑（M0～M7 主线 + M8 增强），建议拆成 **8 个正式版本**提交到 GitHub。  
节奏可按「一天一版」或「两三天一版」，以**每版能演示、能验收**为准，不必死磕一天。

| 版本号 | 对应里程碑 | 一句话目标 | 建议耗时 |
|--------|------------|------------|----------|
| **v1**（本文） | M0 脚手架 | 仓库骨架 + 健康检查 + 前后端能跑起来 | 0.5～1 天 |
| **v2** | M1 资产与会话 | 上传商品图 + 建编辑会话 + 画布显示图片 | 1～2 天 |
| **v3** | M2 工具 + SSE | 手动去背/调色等 + Worker + 进度推送 + 导出 | 2～3 天 |
| **v4** | M3 Agent | LangGraph 计划→确认→执行（电商话术） | 2～3 天 |
| **v5** | M4 文生图 | 创作页生成候选图并进入编辑器（可先 mock） | 1～2 天 |
| **v6** | M5 选区 | 矩形/笔刷选区 + 局部调色 | 2～3 天 |
| **v7** | M6 图层 | 主体/背景拆分基础 + 图层面板 | 2～3 天 |
| **v8** | M7 部署硬化 | 应用也进 Docker，CentOS 一键演示验收 | 1～2 天 |
| （可选）v9+ | M8 增强 | 登录强化、营销图、批量、SAM、COS 等 | 按需 |

**主线完成以 v8 为准**（可对外演示完整电商修图故事）。  
v9 起是加分项，不阻塞「项目做完」的定义。

```text
v1 骨架 → v2 看见商品图 → v3 能手动修 → v4 能说话修
                                              ↓
v8 部署验收 ← v7 图层 ← v6 选区 ← v5 文生图 ←─┘
```

> 中间件 PostgreSQL / Redis 已在虚拟机容器中部署完成，**不计入 v1 编码工作量**，但 v1 的配置要能连上它们。

## 2. 为什么第一版只做「脚手架」？

### 2.1 原则

1. **先搭骨架，再填业务**：目录与分层一次定对，后面每版只加文件，不推倒重来。  
2. **每版必须可运行、可提交**：v1 验收是 `health` 通 + 前端打开，而不是「空文件夹」。  
3. **不提前写 Agent / 抠图**：那些依赖会话、工具注册表、队列，放在 v3/v4，避免半成品堆积。  
4. **对接已有基础设施**：虚拟机上已有 PG(`7311`) / Redis(`7312`)，v1 用环境变量连过去并在 health 里探测。

### 2.2 v1 明确不做（留给后续版本）

| 不做 | 放到哪一版 |
|------|------------|
| 图片上传、画布显示商品图 | v2 |
| ToolRegistry、去背/调色、Worker、SSE | v3 |
| LangGraph Agent、计划卡片 | v4 |
| 文生图、选区、图层、完整 Docker 应用镜像 | v5～v8 |
| 登录注册强制鉴权 | v8 或可选增强 |

## 3. 第 1 版（v1）要完成什么？

### 3.1 交付目标（验收标准）

完成 v1 后，你应能：

1. 在 Windows 上启动后端：`uvicorn` 监听 `7302`  
2. 浏览器或 curl 访问：`GET http://127.0.0.1:7302/api/health`  
3. 返回 JSON 中能看到 PostgreSQL / Redis 连通状态（连虚拟机 `192.168.137.128`）  
4. 启动前端 Vite，打开首页（落地页占位即可），标题体现「电商商品视觉 / image100」  
5. 前端开发代理能把 `/api` 转到后端  
6. 仓库具备 `.gitignore`、`.env.example`、`README.md` 启动说明  
7. **提交到 GitHub**（建议 tag：`v1.0.0` 或 commit message 含 `feat(v1): ...`）

## 4. 后端：v1 要完成哪些文件？

### 4.1 必须完成的文件清单

| 文件 | 职责 | v1 要做到什么 |
|------|------|----------------|
| `backend/pyproject.toml`（或 `requirements.txt`） | 依赖声明 | 至少：`fastapi`、`uvicorn[standard]`、`pydantic-settings`、`sqlalchemy[asyncio]`、`asyncpg`、`redis`、`httpx` |
| `backend/.env.example` | 环境变量模板 | 含 `DATABASE_URL`、`REDIS_URL`、`API_PORT`、`CORS` 等 |
| `backend/app/__init__.py` | 包标识 | 可空 |
| `backend/app/config.py` | 配置单例 | 用 pydantic-settings 读取环境变量；**禁止**业务里散落 `os.getenv` |
| `backend/app/db.py` | 异步引擎 | 创建 async engine / session factory；提供探测连通的函数 |
| `backend/app/deps.py` | 依赖注入入口 | 提供 `get_settings`；为后续 `get_db` 留好位置（可先简单实现） |
| `backend/app/main.py` | 应用入口 | `create_app()`：CORS、挂载 `/api` 路由 |
| `backend/app/routers/__init__.py` | 路由汇总 | `api_router.include_router(health.router)` |
| `backend/app/routers/health.py` | 健康检查 | `GET /api/health`：检查 postgres、redis |
| `backend/app/schemas/__init__.py` | schemas 包 | 可空 |
| `backend/app/schemas/common.py` | 响应模型 | 如 `HealthResponse`（字段：`status`、`postgres`、`redis`） |

### 4.2 v1 后端不写的文件（刻意延后）

`security.py`、`events.py`、`queue.py`、`storage.py`、`worker.py`、`models/*`、`services/*`、`tools/*`、`agent/*`、`providers/*`、`edits/*`、`tasks/*`、`migrations/*`（均可从 **v2** 起按需加入）。

### 4.3 为什么后端这样切？

| 设计 | 原因 |
|------|------|
| 先有 `config` + `db` + `routers/health` | 验证「能连虚拟机 PG/Redis」，后面所有业务都建立在这之上 |
| `routers` 保持薄 | 符合规划：路由只接请求，逻辑以后进 `services` |
| `schemas` 先建 `common` | 统一响应形状，避免前端以后解析一堆裸 dict |
| 暂不建 Alembic / 业务表 | v1 无业务写入；表结构随 v2 上传/会话一起做，避免空迁移 |

### 4.4 v1 推荐环境变量（连已部署的虚拟机）

```env
APP_ENV=development
API_PORT=7302

# 虚拟机中间件（按实机 IP；若只在虚拟机本机跑后端则改 127.0.0.1）
DATABASE_URL=postgresql+asyncpg://retouch:retouch_dev@192.168.137.128:7311/retouch
REDIS_URL=redis://192.168.137.128:7312/0

CORS_ORIGINS=http://localhost:7301,http://127.0.0.1:7301
```

`GET /api/health` 期望示例：

```json
{
  "status": "ok",
  "postgres": "ok",
  "redis": "ok"
}
```

若某一依赖不通，对应字段为 `"error"`，整体 `status` 可为 `"degraded"`（实现时选定一种约定并写进 README）。

### 4.5 v1 后端验收命令

```bash
cd backend
# 安装依赖后
uvicorn app.main:app --reload --host 0.0.0.0 --port 7302

# 另开终端
curl http://127.0.0.1:7302/api/health
```

## 5. 前端：v1 要完成哪些文件？

### 5.1 必须完成的文件清单

| 文件 | 职责 | v1 要做到什么 |
|------|------|----------------|
| `frontend/package.json` | 依赖与脚本 | React 19 + Vite + TypeScript + react-router-dom；脚本含 `dev` / `build` |
| `frontend/vite.config.ts` | 开发服务器 | 端口建议 `7301`；`proxy['/api'] → http://127.0.0.1:7302` |
| `frontend/index.html` | HTML 入口 | 挂载 `#root` |
| `frontend/tsconfig*.json` | TS 配置 | 与 Vite React 模板一致即可 |
| `frontend/src/main.tsx` | 入口 | 渲染 `App`，可包一层 `BrowserRouter` |
| `frontend/src/App.tsx` | 路由壳 | 至少路由到落地页 |
| `frontend/src/index.css` | 全局样式 | 简单干净即可，不必还原完整设计系统 |
| `frontend/src/pages/LandingPage.tsx` | 落地页 | 展示产品名（电商商品视觉 / image100）、一句话介绍、显示后端 health 状态（推荐） |
| `frontend/src/api/client.ts` | API 封装 | `getHealth()` 请求 `/api/health`（推荐，为 v2 打基础） |

### 5.2 v1 前端不写的文件（刻意延后）

| 延后内容 | 版本 |
|----------|------|
| `EditorPage`、`CanvasStage`、react-konva 画布 | v2 |
| 工具栏、Agent 对话、计划卡片 | v3 / v4 |
| Zustand 复杂 store、TanStack Query 全面接入 | v2 起按需 |
| 登录页、创作页四宫格 | v5 / 增强 |

### 5.3 为什么前端这样切？

| 设计 | 原因 |
|------|------|
| 先落地页 + health 展示 | 证明前后端联通，提交 GitHub 时有「看得见」的成果 |
| Vite 代理 `/api` | 开发和以后 Nginx 同源思路一致，少配跨域 |
| 暂不引入 konva | 画布是重模块，和「上传会话」绑定，适合 v2 一起做 |
| 保留 React 栈 | 与规划一致，避免换框架消耗版本预算 |

### 5.4 v1 前端验收命令

```bash
cd frontend
npm install
npm run dev
# 浏览器打开 http://localhost:7301
# 页面应能打开；若做了 health 展示，应显示 postgres/redis 状态
```

## 7. v1 开发顺序（建议严格按此写代码）

1. 建 `backend/` 依赖与 `config.py`  
2. 写 `db.py` + Redis 探测（可用 `redis.asyncio`）  
3. 写 `routers/health.py` + `main.py`，curl 调通  
4. 用 Vite 初始化 `frontend/`（React + TS）  
5. 配 `vite.config.ts` 代理  
6. 写 `LandingPage`（+ 可选 health 展示）  
7. 写 `README.md` / `.gitignore`  
8. 本地自测通过后 **提交 GitHub（v1）**

符合项目规则：改动前可再对一下本文清单；关键连通逻辑加中文注释；不擅自实现 v2 范围。
