```text
v8：原仓前端 + 契约对齐 + COS

```

| 版本 | 口径 |
|------|------|
| v9 | 修图工具与前端驱动补齐；Docker 不做 |
| **v10（本文）** | **用户侧完整**：真账号、个人主页、会员积分、邀请码、生产级配额、Agent 可观测（LangSmith） |
| v11 | Docker；原仓后端收口中偏「重能力」的项 |

**原则**：

1. **本版不做 Docker**（明确顺延 v11）。  
2. **本版不再扩修图工具面**（消除/替换云端、rembg、批量增强等 → v11）。

4. **多租户 = 用户级数据隔离**（与原仓一致），不是企业级 Org/Workspace 计费中台。  
5. 改动前你确认 §11；确认前不写代码。

## 3. 第 10 版验收标准

### 3.1 账号与鉴权

1. **真注册落库**：账号（登录名）+ 用户名（展示名）+ 密码 + **密码二次确认**（前端校验一致；后端也校验）。  
2. **真登录**：账号密码校验；错误提示明确。  
3. **保留 demo 一键**（`demo` / `demo123`），demo 也有积分/会员字段，便于演示。  
4. Cookie / JWT 会话与原仓同类；未登录访问工作台跳转登录页。

### 3.2 个人主页

1. 工作台左下角头像（或用户区）**点击进入个人主页**（不再直接等于退出）。  
2. 个人主页至少展示：账号、用户名、会员等级、当前积分、累计消耗积分、注册时间、签到状态。  
3. 提供：**每日签到**、**模拟充值**、**生成邀请码**、**积分流水列表**、**退出登录**。  
4. 建议补充（本版一并做，见 §5.4）：修改用户名、修改密码、用量摘要（今日已用额度 / 并发占用）。

### 3.3 积分与会员

1. 新用户注册赠送 **2000** 积分。  
2. 会员等级：`青铜 → 白银 → 黄金 → 铂金 → 钻石`（默认青铜）。  
3. **按累计消耗积分**升档（阈值见 §11 默认；可改）。  
4. 每日签到领积分；**等级越高签到越多**（数值见 §11）。  
5. 模拟充值：用户输入金额数字（如 `10`），按 **1 元 = 10 积分**（即 10 元 → 100 积分）入账；**无真实支付**。  
6. 消耗类操作写积分流水；余额不足时 API 返回明确错误，前端 Toast 提示。

### 3.4 邀请码

1. 已登录用户可生成 **五位**邀请码（大写字母 + 数字）。  
2. **时效 10 分钟**；过期后旧码失效，需重新生成。  
3. 同时仅保留 **1 个有效码**（新生成使旧码失效）。  
4. **登录页与注册页**均可选填邀请码；个人中心「邀请」页可对未领过奖励的用户补填一次。填写且码有效时：**填写者与生成者各 +200 积分**。  
5. 每个用户一生仅成功领取 1 次邀请奖励；不能用自己的码给自己；码无效/过期有明确提示。

### 3.5 多租户与生产级配额

1. **多租户（用户级）**：任意 session / asset / batch / run 均校验 `user_id`；越权 403/404。  
2. **配额**：  
   - AI 相关操作扣积分（文生图、Agent 回合、云端编辑类；纯本地像素工具可 **0 积分** 或极低，见 §11）。  
   - 按会员档位有 **每日 AI 次数上限** 与 **并发 run 上限**。  
   - 超限返回可读错误（积分不足 / 今日额度用尽 / 并发已满）。  
3. 个人主页可见今日额度与积分余额。

### 3.6 监控（LangSmith）

1. `.env` 配置 `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT` 后，Agent / LangGraph / LLM 调用可在 LangSmith 控制台看到 trace。  
2. 无 Key 或 tracing 关闭时，业务功能仍可用（监控降级，不阻断）。  
3. 保留现有 `GET /api/health`；本版不引入 Prometheus 全家桶。

**验收一句话**：新用户可注册（含用户名与二次密码）→ 获 2000 积分 → 个人主页签到/模拟充值/邀请 → 登录可用邀请码双方加分 → 修图/生成受积分与日配额约束 → Agent 链路可在 LangSmith 观测。

## 4. 账号模型与注册/登录交互

### 4.1 字段约定

| 字段 | 含义 | 规则（建议） |
|------|------|----------------|
| `account` | 登录账号 | 3–32，字母数字下划线；唯一 |
| `display_name` | 用户名（展示） | 1–32，可中文；个人主页与侧栏显示 |
| `password` | 密码 | 6–64；注册需二次确认一致 |
| `member_tier` | 会员等级 | 青铜…钻石 |
| `points_balance` | 当前积分 | ≥ 0 |
| `points_spent_total` | 累计消耗 | 用于升档 |
| `last_checkin_date` | 上次签到日 | 按服务器日期防重复 |

> 说明：原仓只有 `username`。本仓拆成 **账号 + 用户名**，避免「登录名」和「昵称」混用。前端侧栏头像旁显示 `display_name`。

### 4.2 注册页

- 账号、用户名、密码、确认密码。  
- 前端：确认密码不一致不可提交；账号格式校验。  
- 后端：二次校验密码一致；账号冲突 409。  
- 成功：写用户、赠 2000 积分、写流水「注册赠送」、签发 Cookie，进入工作台。

### 4.3 登录页

- 账号、密码；**可选邀请码**。  
- 邀请码仅在「该账号尚未绑定过此次邀请关系 / 未兑换过该码」时生效（细则：每个码可被多名新用户使用？→ **建议：一码可被多人使用直到过期，但每个用户全局只能成功兑一次邀请奖励**；生成者每次成功兑换各得 200。见 §11）。

### 5.2 会员升档（按累计消耗）

| 等级 | 累计消耗积分门槛（建议默认） |
|------|------------------------------|

### 5.3 签到

| 等级 | 每日签到积分（建议默认） |
|------|--------------------------|
| 青铜 | 20 |
| 白银 | 40 |
| 黄金 | 60 |
| 铂金 | 100 |
| 钻石 | 150 |

同一自然日仅一次；已签到按钮置灰并提示「今日已签到」。

### 5.4 模拟充值

- 弹窗输入金额（正整数，单位：元）。  
- 入账积分 = `金额 × 10`（10 元 → 100 积分）。  
- 流水类型：`mock_recharge`；备注含「模拟充值 ¥N」。  
- 可设单次上限（如 10000 元）防误填；**无真实扣款**。

### 5.5 积分消费（与配额挂钩）

| 操作类型 | 建议扣分 | 说明 |
|----------|----------|------|
| Agent 一轮（规划+执行） | 50 | 含 LLM |
| 文生图 / 营销生成 | 80 | |
| 云端局部编辑（若已接通） | 60 | 未接通则暂不产生 |
| 本地工具（提亮/翻转/裁剪等） | 0 | 鼓励常用修图 |

余额不足：阻断该操作，提示去充值（模拟）或签到。

### 5.6 生产级配额（按会员）

| 等级 | 每日 AI 次数上限 | 并发 run 上限 |
|------|------------------|---------------|
| 青铜 | 20 | 1 |
| 白银 | 50 | 2 |
| 黄金 | 100 | 3 |
| 铂金 | 200 | 4 |
| 钻石 | 500 | 5 |

「AI 次数」= 扣积分的操作次数；本地 0 分工具不计入日额度。

### 5.7 本版建议一并补齐的用户能力

| 能力 | 理由 |
|------|------|
| 积分流水 | 可审计；客服/自查必备 |
| 修改用户名 | 个人主页基础 |
| 修改密码 | 账号安全基础 |

| 邀请成功记录 | 生成者可见「谁用了码 / 获得多少」 |
| 注册协议短提示 | 「模拟充值非真实支付」免误解 |

## 6. 邀请码规则（落地细节）

```text
字符集：A-Z + 0-9（排除易混 I/O/0/1 可选，默认不做排除以保持简单）
长度：5
TTL：600 秒
存储：Redis 优先（key=invite:{code} → inviter_user_id, expires_at）；无 Redis 时可用 DB 表
生成：POST /api/account/invite-codes → { code, expires_at }
兑换：登录（或注册成功后的首次登录）携带 invite_code
奖励：inviter +200，invitee +200；各写流水
约束：
  - 不可自邀
  - 同一 invitee 仅可成功领取「邀请奖励」一次（防刷）
  - 码过期或无效 → 400 + 中文 detail
```

## 7. 监控方案：LangSmith（推荐）+ 轻量健康检查

### 7.1 为什么用 LangSmith，而不是先上 Prometheus

本项目核心差异能力是 **LangGraph Agent + DashScope**。LangSmith 与 LangChain/LangGraph **原生对接**，适合看：

- 某次 Agent 规划为何选错工具  
- LLM 延迟、报错、token/费用相关线索  
- 按用户 / session 过滤调试（可在 trace metadata 打 `user_id`）

它**不能替代**整机监控（CPU、磁盘、Postgres 挂了）。本版组合：

| 层 | 方案 | 本版 |
|----|------|------|
| Agent / LLM | **LangSmith tracing** | 做 |
| 进程存活 | 现有 `/api/health`（postgres/redis/storage） | 保持 |
| 业务审计 | 积分流水 + 结构化日志（user_id, action） | 做 |
| Prometheus / Grafana | 全站指标 | **顺延** |

结论：**LangSmith 是本项目最合适的「智能体可观测」方案**；你已在 `.env` 预留 Key，本版正式接入标准环境变量名。

### 7.2 环境变量（请将 `.env` 里注释的 `LangSmith=...` 改成下列正式名）

```env
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=你的密钥
LANGSMITH_PROJECT=image100
# 若账号非默认区，再设 LANGSMITH_ENDPOINT=...
```

> 兼容：旧名 `LANGCHAIN_TRACING_V2` / `LANGCHAIN_API_KEY` 仍可能被 SDK 识别；**新配置统一用 `LANGSMITH_*`**。  
> **勿把真实 Key 写进文档或提交到 Git**；`.env` 保持本地，仅 `.env.example` 写占位符。

### 7.3 接入范围

- Agent 图执行、Planner LLM、（若有）图像模型调用包装处开启 tracing。  
- metadata 建议：`user_id`、`session_id`、`run_id`。  
- `LANGSMITH_TRACING=false` 或无 Key：静默跳过。
