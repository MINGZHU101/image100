## 1. 第二版要解决什么问题？

v1 只证明「系统能启动、PG/Redis 能连」。v2 要交出产品故事的**第一帧业务画面**：

1. **图片能存住**：multipart 上传商品图，校验类型/大小，落本地盘，元数据进 PostgreSQL。  
2. **会话能建起**：基于某张资产创建 `edit_sessions`，`document` JSONB 描述单主图层画布。  
3. **前端能看见**：落地页上传 → 自动建会话 → 进入编辑器 → Konva 显示该图（可缩放/平移）。  
4. **存储可探活**：health 增加 `storage`，证明本地目录可写。

## 4. 后端完成了什么？

### 4.1 能力清单

1. 配置增加 `STORAGE_BACKEND`、`LOCAL_STORAGE_DIR`、`UPLOAD_MAX_BYTES`；存储根目录相对**项目根** `image100/data`。  
2. Alembic 管理表结构；首迁创建 `users` / `assets` / `edit_sessions`，并种子 `demo` 用户（固定 UUID）。  
3. 本地存储：`put` / `get` / `exists` / 可写探测；key 形如 `objects/{uuid}.png`。  
4. 资产 API：上传（MIME/大小/Pillow 校验）、列表、按 id 返回文件流。  
5. 会话 API：按 `asset_id` 建会话并写入单图层 `document`；按 id 查询。  
6. health 并行探测 postgres + redis，线程池探测 storage。  
7. 分层保持：`routers` 薄 → `services` 编排 → `models` + `storage`。

### 4.2 依赖增量（`pyproject.toml`）

| 包 | 用途 |
|----|------|
| `alembic` | 数据库迁移 |
| `python-multipart` | 上传表单解析 |
| `pillow` | 校验图片并读取宽高 |

（v1 已有的 fastapi / uvicorn / sqlalchemy / asyncpg / redis / httpx / pydantic-settings 继续使用。）

### 4.3 环境变量（v2 生效）

| 变量 | 含义 | 示例 |
|------|------|------|
| `STORAGE_BACKEND` | 存储后端 | `local` |
| `LOCAL_STORAGE_DIR` | 相对项目根的存储目录 | `./data` |
| `UPLOAD_MAX_BYTES` | 上传上限 | `10485760`（10MB） |

演示用户常量（代码内，与迁移一致）：

- `DEMO_USER_ID = 00000000-0000-0000-0000-000000000001`  
- `username = demo`（v2 无登录校验）

### 4.4 接口一览

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/health` | `{status, postgres, redis, storage}` |
| POST | `/api/assets` | `multipart` 字段 `file` |
| GET | `/api/assets` | 资产列表（含 `file_url`） |
| GET | `/api/assets/{id}/file` | 图片二进制 |
| POST | `/api/sessions` | body `{ "asset_id" }` |
| GET | `/api/sessions/{id}` | 会话 + document |

### 4.5 会话 `document` 结构

```json
{
  "version": 1,
  "canvas": { "width": 320, "height": 240 },
  "layers": [
    {
      "id": "layer_main",
      "name": "主图层",
      "asset_id": "<uuid>",
      "asset_key": "objects/<uuid>.png",
      "visible": true
    }
  ],
  "selection": null
}
```

`canvas` 宽高取自上传图真实像素。

#### `app/config.py` — 配置中心【改】

| 项 | 说明 |
|----|------|
| **一句话** | 集中读取 `.env`；v2 在 v1 基础上增加「本地存储」相关配置。 |

**文件里有什么**

#### `app/db.py` — 引擎、Session、三项探活【改】

| 项 | 说明 |
|----|------|
| **一句话** | 连 PostgreSQL 的异步基础设施 + PG/Redis/本地盘是否可用。 |

**相对 v1 增加了什么**

- 函数 `check_storage()`：内部 `from app.storage import get_storage`，再调 `check_writable()`，返回 `"ok"` / `"error"`。

**仍保留的 v1 能力**

**v2 为何 Session 变得重要**

- 上传写 `assets`、建会话写 `edit_sessions`，都通过 `deps.DbDep` → `get_session()` 拿到同一个请求级 Session，再 `commit`。

**怎么读**：在 v1 理解基础上，多看文件末尾的 `check_storage`。

#### `app/storage.py` — 本地磁盘存储【新】

| 项 | 说明 |
|----|------|
| **一句话** | 把图片字节写到 / 从 `data/` 读出来；接口设计成以后可换成腾讯云 COS。 |

**文件里有什么**

1. **`Storage`（Protocol）**  
   约定方法：`ensure_ready`、`put`、`get`、`exists`、`absolute_path`、`check_writable`。  
   这是「接口」，不是具体实现——以后加 `CosStorage` 时，service 层尽量只依赖这套方法名。

2. **`LocalStorage`（实现）**  
   - 根目录：`settings.storage_root`（默认项目根下 `data/`）。  
   - `ensure_ready()`：创建 `data/` 与 `data/objects/`。  
   - `_resolve(key)`：把 `objects/xxx.png` 拼成绝对路径，并检查**不能路径穿越**到根目录之外。  
   - `put(key, data, content_type)`：自动建父目录后写文件。  
   - `get` / `exists` / `absolute_path`：读字节、判断存在、给 `FileResponse` 用路径。  
   - `check_writable()`：写一个临时探测文件再删掉，供 health 使用。

3. **`get_storage()`**  
   进程内单例；若 `STORAGE_BACKEND` 不是 `local`，直接报错（v2 不做其它后端）。

**典型 key**：`objects/{uuid}.png`（与数据库 `assets.storage_key` 一致）。

**和谁联动**

| 调用方 | 场景 |
|--------|------|
| `services/assets.upload_asset` | 上传成功后 `put` |
| `routers/assets.get_asset_file` | `exists` + `absolute_path` 后返回文件 |
| `db.check_storage` | health 探活 |

**怎么读**：先看 Protocol 方法列表，再看 `LocalStorage.put` 和 `_resolve` 的安全检查。

### 5.4 服务层 `app/services/`【新】——「真正干活的用例」

> 路由只接 HTTP；**校验、写盘、写库、拼 document 都在 service**。

#### `services/__init__.py`

- 包标记，可空。

#### `services/assets.py` — 资产用例

| 项 | 说明 |
|----|------|
| **一句话** | 上传图片、列资产、按 id 取资产行。 |

**核心函数逐步说明**

1. **`upload_asset(session, upload)`**（最重要）  
   - 检查 `Content-Type` 是否在 jpeg/png/webp 白名单。  
   - `await upload.read()` 得到字节；空文件 / 超过 `upload_max_bytes` 则 400。  
   - 用 Pillow `Image.open` 校验确为图片，读取 `width/height`，并按真实格式决定后缀。  
   - 生成新 UUID 作为资产 id；`storage_key = objects/{id}.ext`。  
   - `get_storage().put(...)` 写磁盘。  
   - `Asset(...)` 写入数据库，`owner_id=DEMO_USER_ID`，`commit` + `refresh`。  
   - 返回 `AssetOut`（含 `file_url`）。

2. **`list_assets`**：`SELECT` 按 `created_at` 倒序。  
3. **`get_asset_or_404`**：没有则抛 404，供取文件和建会话复用。  
4. **`to_asset_out` / `asset_file_url`**：ORM → API 模型。

**联动**

```text
POST /api/assets
  → routers/assets.upload_asset
  → services/assets.upload_asset
       ├─ config（大小上限、demo 用户）
       ├─ Pillow 校验
       ├─ storage.put → data/objects/...
       └─ models.Asset → PostgreSQL
```

---

#### `services/sessions.py` — 会话用例

| 项 | 说明 |
|----|------|
| **一句话** | 根据一张资产创建编辑会话，并生成初始画布 document。 |

**核心函数**

1. **`build_document(asset_id, storage_key, width, height)`**  
   返回规划约定的 JSON：version、canvas、单层 `layer_main`、selection=null。

2. **`create_session(session, asset_id)`**  
   - 先 `get_asset_or_404`（资产必须存在）。  
   - `build_document` 用资产真实宽高。  
   - 插入 `EditSession(title="商品编辑", document=...)`。  
   - 返回 `SessionOut`。

3. **`get_session`**：按 UUID 取会话，没有则 404。

**联动**

```text
POST /api/sessions {asset_id}
  → routers/sessions
  → services/sessions.create_session
       ├─ services/assets.get_asset_or_404
       └─ models.EditSession → PostgreSQL
```

### 5.5 路由层 `app/routers/`——「HTTP 门面」

#### `routers/__init__.py`【改】

```text
api_router
  ├─ health.router
  ├─ assets.router      # /api/assets...
  └─ sessions.router    # /api/sessions...
```

---

#### `routers/health.py`【改】

| 项 | 说明 |
|----|------|
| **一句话** | health 现在查三样：PG、Redis、本地存储。 |

**流程**

1. `asyncio.gather(check_postgres(), check_redis())` 并行。  
2. `asyncio.to_thread(check_storage)`：磁盘探测是同步 IO，放到线程池，避免卡住事件循环。  
3. 三者都 ok → `status=ok`，否则 `degraded`；HTTP 仍 200。  
4. 返回四字段 `HealthResponse`。

---

#### `routers/assets.py`【新】

| 路径 | 方法 | 做什么 |
|------|------|--------|
| `/api/assets` | POST | 表单字段名必须是 `file`；调 `services.assets.upload_asset` |
| `/api/assets` | GET | 返回 `{items: [...]}` |
| `/api/assets/{id}/file` | GET | 查库拿 `storage_key` → 磁盘路径 → `FileResponse` |

**设计选择**：用「按 id 取文件」而不是静态 `/media`，便于以后加鉴权、也不暴露真实磁盘布局。

---

#### `routers/sessions.py`【新】

| 路径 | 方法 | 做什么 |
|------|------|--------|
| `/api/sessions` | POST | JSON `{asset_id}` → 建会话 |
| `/api/sessions/{id}` | GET | 返回会话 + document |

**原则**：路由函数尽量短，复杂逻辑一律在 service。

### 5.6 迁移文件（`backend/migrations/`，配合 models）

| 文件 | 一句话 | 详细作用 |
|------|--------|----------|
| `alembic.ini` | Alembic 工具配置 | `script_location=migrations`；里面的 URL 是占位，真正 URL 由 env.py 覆盖 |
| `migrations/env.py` | 迁移运行环境 | 读 `Settings.database_url`；`import app.models` 注册表；用异步引擎执行 |
| `.../20261015_0001_v2_assets_sessions.py` | 首条迁移 | `upgrade`：建 `users`/`assets`/`edit_sessions` 并 INSERT demo 用户；`downgrade`：删表 |

**你需要记住的命令**

```bash
cd backend
python -m alembic upgrade head   # 把「图纸」应用到虚拟机 PostgreSQL
```

换一台新库、或别人刚 clone 项目时，都要先跑这句，否则上传会报「表不存在」。

### 一次「上传 → 建会话 → 看图」时序

1. 前端 `POST /api/assets`（multipart `file`）。  
2. `services/assets` 校验 → 写 `data/objects/...` → 插入 `assets` 行。  
3. 前端 `POST /api/sessions` `{asset_id}`。  
4. `services/sessions` 生成 document → 插入 `edit_sessions`。  
5. 前端进入 `/editor/{sessionId}`，`GET /api/sessions/{id}`。  
6. 画布请求 `GET /api/assets/{asset_id}/file`，后端 `FileResponse` 读本地文件。  
7. Konva 渲染图片。

## 7. 前端完成了什么？

### 7.1 能力清单

1. 依赖增加 `konva`、`react-konva`。  
2. `api/assets.ts` / `api/sessions.ts`：上传、建会话、拉会话。  
3. `ImageUpload`：选图 → 上传 → 自动建会话 → `navigate(/editor/:id)`。  
4. `EditorPage`：按路由加载会话，解析主图层，把 URL/尺寸交给画布。  
5. `CanvasStage`：Konva Stage 显示图片；滚轮缩放、拖拽平移；按容器尺寸初始适配。  
6. 落地页保留 health（含 storage），并嵌入上传入口。  
7. 路由：`/` 落地页，`/editor/:sessionId` 编辑器。
