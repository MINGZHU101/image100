> - `电商商品视觉生产_版本规划与v1交付说明.md`

## 1. v4 在整条版本线里的位置

```text
v1 骨架 → v2 看见商品图 → v3 能手动修 → ★ v4 能说话修
                                              ↓
v8 部署验收 ← v7 图层 ← v6 选区 ← v5 文生图 ←─┘
```

| 版本 | 里程碑 | 用户能感知到什么 |

| v1 | M0 | 系统能启动，health 通 |
| v2 | M1 | 上传后画布看得见商品图 |
| v3 | M2 | 点工具栏能修图，有进度，能导出 |

v4 把编辑器从「人手点工具」升级为「自然语言驱动」。**不重写像素执行**：确认后的每一步仍走 v3 已有的 ToolRegistry → ARQ → SSE 闭环。

## 2. 为什么第四版做「Agent 计划 + 人机确认」？

### 2.1 原则（延续 v1～v3）

1. **每版可演示**：验收题是「输入电商话术 → 看到计划 → 确认后画布变了」，不是半截 LangGraph 空壳。  
2. **计划与执行分离**（规划书 8.3）：图里只做 `plan → verify → END`；**不在图内连跑像素**。  
3. **ToolRegistry 仍是唯一真相源**：Agent 只能调用 `agent_exposed=True` 的工具；禁止 Agent 旁路写第二套修图逻辑。  
4. **人机确认是产品能力**（规划书 8.4）：多步计划默认必须确认后再入队。  
5. **Provider 可切换**：默认 `PLANNER_PROVIDER=mock`（无 Key 可演示）；有 Key 时切 `dashscope`。  
6. **复用 v3 异步链路**：确认后按序 `enqueue` 已有工具；进度仍走 `/api/events/{run_id}`。

### 2.2 v4 明确不做（留给后续版本）

| 不做 | 放到哪一版 | 原因 |
|------|------------|------|
| 文生图创作页、`POST /api/generations` | v5 | 另一入口，不阻塞「说话修」 |
| 矩形/笔刷选区、局部编辑 | v6 | 画布交互加重；Agent 本版只规划整图工具 |
| 主体/背景拆层、完整图层面板 | v7 | 图层模型后续扩展 |
| 强制登录、COS、应用 Docker 全量 | v8 / 增强 | 不阻塞 Agent 主路径 |
| 图内自动连跑、无人确认开环 | 增强（可选配置） | 一期默认关；可控费用与副作用 |
| 参考仓库全量对话历史/多 Agent | 不做 | 单会话、单次 goal→plan 够演示 |
| rembg / SAM / 新像素工具大扩容 | 增强 | v3 工具够用；Agent 只编排已有工具 |

## 3. 第 4 版要完成什么？（验收标准）

完成 v4 后，你应能：

1. 编辑器侧栏（或底部）出现 **Agent 对话区**：可输入自然语言 goal。  
2. `POST /api/sessions/{id}/agent/runs` 提交 goal 后，返回 `{agent_run_id, reply, plan}`（计划为工具步骤列表）。  
3. 前端展示 **计划卡片**（每步：工具中文名、关键参数摘要）；用户可 **确认** 或 **取消**。  
4. `POST .../agent/runs/{id}/confirm` 后，后端按计划**顺序**为每步创建 `tool_runs` 并 ARQ 入队（复用 v3）。  
5. 执行过程中能看到进度（复用工具 SSE；可选 `step_done` 事件）；全部完成后画布更新。  
6. 无 DashScope Key 时，`PLANNER_PROVIDER=mock` 仍能产出合理计划（例如对「去背再提亮」返回 `remove_background` → `adjust_image`）。  
7. 库中有 `agent_runs` 表；非法工具名 / 参数在 **verify** 阶段失败并返回中文原因，不入队。  
8. README 写明：Agent 相关环境变量 + 仍需 API + Worker；提交 GitHub，tag 建议 `v4.0.0`。

**验收一句话**：上传商品图 → 输入「去掉背景，再提亮一点」→ 计划卡片确认 → 进度走动 → 画布更新。

**电商话术验收题（对齐规划书第 3 章）**：

| 难度 | 示例 goal | 期望 |
|------|-----------|------|
| 简单 | 「亮度提高一点」 | 单步 `adjust_image` |
| 中等 | 「去掉背景」 | 单步 `remove_background` |
| 困难 | 「去背、提亮」 | 两步：`remove_background` → `adjust_image` |
| 陷阱 | 「用某某未注册滤镜」 | verify 失败，中文错误，不执行 |

## 4. 主流程（用户路径）

```text
用户在 Editor 输入：「去掉背景，再提亮一点」
  → POST /api/sessions/{id}/agent/runs  { "goal": "..." }
  → services/agent：
       组装画布上下文 + 仅 agent_exposed 工具 schema
       → agent/graph：plan → verify
       → 写 agent_runs(status=planned, plan=JSON)
  → 返回 { agent_run_id, reply, plan }

前端：
  → 展示 PlanCard（步骤列表）
  → 用户点「确认执行」

  → POST /api/sessions/{id}/agent/runs/{agent_run_id}/confirm
  → services/agent：
       status=confirmed → running
       按 plan 顺序：对每步调用既有「写 tool_runs + enqueue」
       （可串行：等上一步 succeeded 再入队下一步；或入队时依赖编排，一期建议串行）
  → 前端对每个 tool run_id 订阅 SSE（或统一进度条）

Worker（v3 已有）：
  → 执行像素工具 → 更新 document → publish completed

全部步骤 done：
  → agent_runs.status=done
  → 前端刷新会话 / 画布
```

**关键约束**：

- LangGraph **不**直接改像素、**不**直接调 Storage。  
- 确认前 **不**创建 `tool_runs`、**不**入队。  
- 取消：`status=cancelled`，已入队步骤按能力尽量不启新任务（一期：未开始的步骤不再 enqueue）。

## 6. 后端：v4 要完成哪些文件？

### 6.1 分层为何这样切

| 层 | 职责 | 为什么 |
|----|------|--------|
| `agent/` | LangGraph plan/verify + prompt | 编排与校验可单测；不碰像素 |
| `providers/` | mock / dashscope 规划器 | 无 Key 可演示；有 Key 切真 LLM |
| `services/agent.py` | 用例：规划落库、确认串行入队 | 事务与状态机边界 |
| `tools/` | 增加 `agent_exposed` | UI 与 Agent 仍共用 Registry |
| v3 `services/tools` + Worker | 真正改像素 | **零重写**，只被 confirm 调用 |

### 6.2 ToolSpec 增量（相对 v3）

在现有 `ToolSpec` 上增加：

| 字段 | 说明 | v4 默认 |
|------|------|--------|
| `agent_exposed` | 是否允许出现在 Agent 工具 schema | `adjust_image` / `remove_background` / `flip_layer` → `True` |
| （可选）`risk_level` | `low` / `medium` / `high` | 一期可一律 `low`；确认策略仍默认「多步必确认」 |

导出仍走同步 HTTP，**不要**放进 Agent 工具列表（或 `agent_exposed=False`）。

### 6.3 计划 JSON 形状（冻结）

```json
{
  "steps": [
    {
      "id": "s1",
      "tool_name": "remove_background",
      "params": {},
      "depends_on": []
    },
    {
      "id": "s2",
      "tool_name": "adjust_image",
      "params": { "brightness": 0.2, "contrast": 0.0, "saturation": 0.0 },
      "depends_on": ["s1"]
    }
  ]
}
```

一期依赖策略：**线性**——后一步 `depends_on` 前一步；不做复杂拓扑调度（规划书 0.5 精简约定）。

### 6.4 `agent_runs` 表（最小字段）

对齐规划书 7.2：

| 字段 | 说明 |
|------|------|
| `id` | UUID |
| `session_id` | FK → edit_sessions |
| `goal` | 用户自然语言 |
| `reply` | Agent 给用户的短回复（中文） |
| `plan` | JSONB，见上 |
| `status` | `planned` / `confirmed` / `running` / `done` / `cancelled` / `failed` |
| `error` | 校验或执行失败信息 |
| `created_at` / `updated_at` | 时间 |

可选增强（非必须）：`current_step_index`、`tool_run_ids` JSONB，便于前端展示「第几步」。

### 6.5 必须完成的后端文件清单

| 文件 | 职责 | v4 要做到什么 |
|------|------|----------------|
| `models/agent_run.py` | ORM | 上表字段 |
| Alembic 迁移 | DDL | 建 `agent_runs` + 索引 |
| `agent/plan.py` | 校验 | 工具存在、agent_exposed、params 过 Pydantic、无环/线性依赖 |
| `agent/graph.py` | LangGraph | `plan → verify`；失败写入可读错误 |
| `agent/llm.py` + `providers/*` | 规划器 | mock 规则规划；dashscope 可选 |
| `agent/prompts.py` | Prompt | 电商话术 + 当前画布摘要 + 工具列表 |
| `services/agent.py` | 用例 | create_run / confirm（串行入队）/ cancel |
| `routers/agent.py` | HTTP | 规划、确认、取消、查询 |
| `schemas/agent.py` | 契约 | 请求/响应模型 |
| `tools/base.py` 等 | Registry | `agent_exposed` + `list_agent_tools()` |
| `config.py` / `.env.example` | 配置 | Planner 相关变量 |
| `pyproject.toml` | 依赖 | langgraph 等 |

### 6.6 接口契约（v4 冻结范围）

在 v3 接口之上新增：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/sessions/{id}/agent/runs` | body `{goal}` → `{agent_run_id, reply, plan, status}` |
| GET | `/api/sessions/{id}/agent/runs/{agent_run_id}` | 查询计划与状态 |
| POST | `/api/sessions/{id}/agent/runs/{agent_run_id}/confirm` | 确认执行 → `{status, tool_run_ids?}` |
| POST | `/api/sessions/{id}/agent/runs/{agent_run_id}/cancel` | 取消（planned 或尚未入队的步骤） |

**不新增像素工具路由**；执行仍走：

- `POST /api/sessions/{id}/tools/{tool_name}`（内部可直接调 `services.tools.invoke_tool`，不必再绕 HTTP）  
- `GET /api/events/{run_id}`（每个 tool_run）

可选 SSE 增强（非阻塞）：在 agent 维度推送 `step_done`（规划书 10.1）；一期也可用前端轮询 `agent_runs` + 订阅各 tool SSE。

### 6.7 Mock 规划器行为（无 Key 必保）

`PLANNER_PROVIDER=mock` 时用**确定性规则**（可查关键词），保证答辩可复现：

| goal 含 | 产出步骤（示例） |
|---------|------------------|
| 去背 / 抠图 / 透明背景 | `remove_background` |
| 提亮 / 亮一点 / 亮度 | `adjust_image`（brightness≈+0.2） |
| 翻转 / 镜像 | `flip_layer` |
| 「去背」+「提亮」同时出现 | 先去背，再提亮 |
| 无法识别 | `plan=[]` + reply 说明可改用工具栏；或 `failed` + 中文原因 |

有 `DASHSCOPE_API_KEY` 且 `PLANNER_PROVIDER=dashscope` 时：LLM 按 schema 产出 plan，**仍必须经 verify**。

### 6.8 与参考仓库的对齐与差异

| 点 | 参考仓库 (ai-picture-editor) | image100 v4 |
|----|------------------------------|-------------|
| LangGraph | plan → verify（及更完整图） | **对齐最小图** `plan → verify → END` |
| 确认后执行 | 入队工具 | **对齐**；调用本仓 v3 `invoke_tool` / enqueue |
| 计划卡片 | 前端有 | **对齐思路**，UI 按本仓编辑器风格 |
| 工具数量 | 较多 | **只用 v3 已注册 3 个**（+ 导出不进 Agent） |
| Provider | 多样 | **默认 mock**，dashscope 可选 |
| 文生图 / 选区 | 仓库可能已有 | **不做**（v5/v6） |
| 存储 | MinIO 等 | 继续 **local** `data/` |

## 8. 进程与启动方式（相对 v3）

开发期仍是 **三个进程**（与 v3 相同）：

```bash
# 终端 1：API
cd backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 7302

# 终端 2：Worker（确认后的步骤仍靠它）
cd backend
python -m arq app.worker.WorkerSettings

# 终端 3：前端
cd frontend
npm run dev
```

**变化点在配置，不在进程数**：

```env
# v4 规划器（默认 mock，无 Key 可演示）
PLANNER_PROVIDER=mock
# PLANNER_PROVIDER=dashscope
# DASHSCOPE_API_KEY=
# DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
# PLANNER_MODEL=qwen-plus
```

README 必须写清：无 Worker 时，确认后的步骤会停在 `queued`；无 Key 时请保持 `PLANNER_PROVIDER=mock`。

## 9. v4 推荐开发顺序

1. 依赖：`langgraph` / `langchain-core`（及可选 OpenAI 兼容客户端）写入 `pyproject.toml` 并安装。  
2. `ToolSpec.agent_exposed` + `list_agent_tools()`。  
3. `models/agent_run.py` + Alembic 迁移并 `upgrade head`。  
4. `agent/plan.py`：PlanStep + validate（先写单测/脚本：未知工具、坏参数）。  
5. `providers/mock.py` + `agent/llm.py`：mock 规划器。  
6. `agent/graph.py`：`plan → verify`。  
7. `services/agent.py` + `routers/agent.py`：规划接口可用 curl 打通。  
8. `confirm`：串行调用 `services.tools.invoke_tool`，联调 Worker。  
9. 前端对话区 + PlanCard + confirm 流。  
10. （可选）`PLANNER_PROVIDER=dashscope` 接通真实 Key。  
11. README、联调、提交 `version4` / tag `v4.0.0`。
