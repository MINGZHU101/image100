> **对应里程碑**：M1 资产与会话

## 1. v2 在整条版本线里的位置


## 2. 为什么第二版只做「资产 + 会话 + 画布显示」？



### 2.1 原则（延续 v1）

1. **每版可演示、可验收**：v2 验收题是「上传后看见图」，不是「空表结构」或「半截工具」。
2. **按依赖顺序加文件**：规划书第 20 章开工顺序：`models + Alembic → storage → assets → sessions → 前端 Editor`。
3. **不提前写 Worker / Agent**：工具执行、SSE、LangGraph 依赖「已有 session.document」；先把会话与图层文档落库，v3/v4 才有意义。
4. **存储先本地盘**：你们已定 `STORAGE_BACKEND=local`，后续再切腾讯云 COS；参考仓库用 MinIO/S3，**接口形态可对齐，实现换成 LocalStorage**。
5. **分层不破**：`routers` 薄、`services` 编排事务、`models` 持久化、`schemas` 定契约——与 v1 / 规划书 / 参考仓库一致。



### 2.2 v2 明确不做（留给后续版本）


| 不做                                | 放到哪一版     | 原因                          |
| --------------------------------- | --------- | --------------------------- |
| ToolRegistry、去背/调色、ARQ Worker、SSE | v3        | 需要会话已存在，且要异步进度              |
| LangGraph、计划卡片、确认执行               | v4        | 依赖工具注册表 + session 上下文       |
| 文生图创作页                            | v5        | 另一条入口，不阻塞「上传→看见」            |
| 选区 / 图层拆分                         | v6 / v7   | 画布交互加重，先保证单图层显示             |
| 强制登录鉴权                            | v8 或增强    | v2 可用默认用户 / 可选 owner，避免卡主路径 |
| 腾讯云 COS / MinIO 真接通               | 增强或 v8 前后 | 协议预留即可，实现仍用本地目录             |

## 3. 第 2 版要完成什么？（验收标准）

完成 v2 后，你应能：

1. 执行 Alembic 迁移，虚拟机 PostgreSQL 中出现至少 `users`（或等价默认归属）、`assets`、`edit_sessions` 表。
2. `POST /api/assets`：multipart 上传一张商品图（jpg/png/webp），文件落到本地 `data/`（或配置的 `LOCAL_STORAGE_DIR`），库中有资产行。
3. `GET /api/assets`：能列出已上传资产（至少含 id、宽高、可访问 URL 或路径信息）。
4. `POST /api/sessions`：传入 `asset_id`，创建编辑会话，`document` JSONB 含单主图层。
5. `GET /api/sessions/{id}`：返回会话 + document。
6. 图片可通过约定方式被前端加载（推荐：`GET /api/assets/{id}/file` 或静态挂载 `/media/...`，二选一并写进 README）。
7. 前端：落地页可进入上传/编辑流程；**Editor 页用 Konva 画布显示该商品图**。
8. `GET /api/health` 增加 **storage** 探测（本地目录可写），与 postgres / redis 一并返回。
9. 更新 README 启动步骤（含 `alembic upgrade head`）；提交 GitHub，tag 建议 `v2.0.0`。

**验收一句话**：打开前端 → 上传商品图 → 自动或手动进入编辑器 → 画布中央能看到这张图。

## 5. 后端：v2 要完成哪些文件？



### 5.1 FastAPI 工程化分层（为何这样切）


| 层    | 目录/文件                            | 职责                          | 为什么                    |
| ---- | -------------------------------- | --------------------------- | ---------------------- |
| 接入层  | `routers/`                       | 解析 HTTP、调 service、返回 schema | 路由保持薄，便于以后加鉴权/限流       |
| 契约层  | `schemas/`                       | 请求/响应形状                     | 前后端对齐，OpenAPI 可生成文档    |
| 应用层  | `services/`                      | 事务边界、用例（上传写库+写盘）            | 避免路由里堆业务               |
| 持久化  | `models/` + Alembic              | 表结构与 ORM                    | JSONB 会话文档落 PG         |
| 基础设施 | `storage.py`、`config.py`、`db.py` | 文件存取、配置、引擎                  | 可替换 COS 而不改 service 签名 |


调用链（上传示例）：

```text
POST /api/assets
  → routers/assets.py
  → services/assets.py（校验 MIME/大小 → storage.put → 插入 Asset）
  → models/asset.py + storage.py
  → schemas/asset.py 响应
```



### 5.2 必须完成的后端文件清单


| 文件                             | 职责             | v2 要做到什么                                                                    |
| ------------------------------ | -------------- | --------------------------------------------------------------------------- |
| `backend/pyproject.toml`       | 依赖             | 增加：`alembic`、`python-multipart`、`pillow`（读宽高）；可选暂不引入 `boto3`                |
| `.env.example` / `config.py`   | 配置             | **生效**：`STORAGE_BACKEND=local`、`LOCAL_STORAGE_DIR=./data`、上传大小上限等；COS 仍注释预留 |
| `alembic.ini` + `migrations/*` | 迁移             | 首条迁移创建 `users`（若需要）、`assets`、`edit_sessions`                                |
| `app/storage.py`               | 存储             | `put` / `get` / `exists` / `public_url_or_path`；本地落盘；目录自动创建                 |
| `app/models/user.py`           | 用户             | 一期可仅种子默认用户，或 `owner_id` 可空；不强制登录 UI                                         |
| `app/models/asset.py`          | 资产 ORM         | 字段对齐规划：`id, owner_id, storage_key, width, height, mime, created_at`         |
| `app/models/edit_session.py`   | 会话 ORM         | `id, owner_id, title, document(JSONB), created_at, updated_at`              |
| `app/schemas/asset.py`         | 资产 API 模型      | 上传响应、列表项（含可访问 URL）                                                          |
| `app/schemas/session.py`       | 会话 API 模型      | 创建请求 `{asset_id}`、详情（含 document）                                            |
| `app/services/assets.py`       | 资产用例           | 上传、列表、按 id 取图；校验扩展名/大小                                                      |
| `app/services/sessions.py`     | 会话用例           | 按 asset 建 session；初始化 `document` 单图层                                        |
| `app/routers/assets.py`        | 资产路由           | `POST /api/assets`、`GET /api/assets`、`GET /api/assets/{id}/file`（或等价）       |
| `app/routers/sessions.py`      | 会话路由           | `POST /api/sessions`、`GET /api/sessions/{id}`                               |
| `app/routers/health.py`        | 健康检查           | 增加 `storage` 字段                                                             |
| `app/schemas/common.py`        | HealthResponse | `{status, postgres, redis, storage}`                                        |
| `app/routers/__init__.py`      | 路由汇总           | include assets、sessions                                                     |
| `app/main.py`                  | 应用入口           | 注册新路由；确保 multipart 可用                                                       |




### 5.3 v2 后端刻意不写的文件

`security.py`（强制鉴权）、`queue.py` / `worker.py` / `events.py`、`tools/*`、`agent/*`、`providers/*`、`tasks/*`、`models/tool_run.py`、`models/agent_run.py`、`services/tools.py`、`services/agent.py` 等——全部留给 **v3/v4**。

### 5.4 库表范围（v2 最小集）

以规划书第 7 章为准，**v2 只建业务所需最小表**：


| 表               | v2     | 说明                                         |
| --------------- | ------ | ------------------------------------------ |
| `users`         | 建议建    | 可 seed 一条 `demo` 用户，便于 `owner_id` 非空；不做登录页 |
| `assets`        | **必须** | 图片元数据                                      |
| `edit_sessions` | **必须** | 含 `document` JSONB                         |
| `tool_runs`     | 不做     | v3                                         |
| `agent_runs`    | 不做     | v4                                         |


**会话** `document` **最小结构（与规划书 7.3 对齐）**：

```json
{
  "version": 1,
  "canvas": { "width": 1024, "height": 1024 },
  "layers": [
    {
      "id": "layer_main",
      "name": "主图层",
      "asset_id": "<uuid>",
      "asset_key": "objects/xxx.png",
      "visible": true
    }
  ],
  "selection": null
}
```

> `canvas.width/height` 建议用上传图真实像素；前端 Konva Stage 按此尺寸或等比缩放显示。



### 5.5 接口契约（v2 冻结范围）


| 方法   | 路径                      | 说明                                   |
| ---- | ----------------------- | ------------------------------------ |
| GET  | `/api/health`           | `{status, postgres, redis, storage}` |
| POST | `/api/assets`           | `multipart/form-data` 字段名建议 `file`   |
| GET  | `/api/assets`           | 资产列表                                 |
| GET  | `/api/assets/{id}/file` | 返回图片二进制（或 302 到静态 URL）               |
| POST | `/api/sessions`         | body：`{ "asset_id": "..." }`         |
| GET  | `/api/sessions/{id}`    | 会话 + document                        |


**上传护栏（规划书安全建议，v2 落地）**：

- MIME / 扩展名白名单：如 `image/jpeg`、`image/png`、`image/webp`  
- 大小上限：建议 **10MB**（配置项，如 `UPLOAD_MAX_BYTES`）  
- 用 Pillow 打开校验确为图片并读取 width/height



### 5.6 本地存储约定


| 项      | 建议                                                             |
| ------ | -------------------------------------------------------------- |
| 根目录    | `LOCAL_STORAGE_DIR=./data`（相对项目根）                              |
| key 形态 | 如 `objects/{uuid}.png`（与参考仓库 key 风格接近，便于以后换 COS）               |
| 实现要点   | `storage.put(key, bytes, content_type)`；`get`；启动或首次写入时 `mkdir` |
| health | 探测目录存在且可写（写临时文件再删，或 `os.access`）                               |
| git    | `data/` 必须在 `.gitignore`                                       |


与参考仓库差异：对方 `storage.py` 基于 boto3/MinIO；我们 v2 用 **LocalBackend**，可在同一文件内预留 `Storage` 协议，方便以后加 `CosBackend`，**不要**在 v2 强依赖 MinIO 容器。

### 5.7 配置增量（在 v1 基础上生效）

```env

REDIS_URL=redis://192.168.137.128:7312/0

# 仍注释预留：JWT、腾讯云 COS、DashScope 等
```



### 5.8 为什么 health 要加 storage？

v1 只证明「库和缓存通」。v2 业务依赖**写文件**；若磁盘路径错误或权限不足，上传会失败。health 带上 `storage`，与参考仓库「三件套探活」思路一致（对方探 bucket，我们探本地目录）。

### 6.3 为什么前端这样切？


| 设计                                   | 原因                                                 |
| ------------------------------------ | -------------------------------------------------- |
| 单独 `EditorPage` + `CanvasStage`      | 编辑器会持续变厚；页面编排与画布渲染分离，符合参考仓库结构                      |
| API 按资源拆 `assets.ts` / `sessions.ts` | 与后端 routers 一一对应，避免 `client.ts` 膨胀                 |
| v2 就引入 Konva                         | 规划书明确 React+Konva；若 v2 用 `<img>` 凑合，v3 工具刷新画布时仍要重写 |
| 上传成功立刻建会话并跳转                         | 最短路径打通「上传→看见」，少一次用户决策                              |
| 暂不上复杂工具栏                             | 工具栏无后端工具可调，会变成空壳误导验收                               |

```text
  → 跳转 /editor/{sessionId}

```

## 8. v2 推荐开发顺序（严格按依赖）
